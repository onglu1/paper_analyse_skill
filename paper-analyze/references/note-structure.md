# 论文精读笔记结构规范

本文件定义了精读笔记的生成规范。子 agent 在生成笔记时必须严格遵循此结构。

---

## 一、笔记整体结构

精读笔记由以下六节组成，按顺序排列：

1. 概览
2. 论文怎么定义问题
3. 相关工作
4. 方法与架构
5. 评测
6. 总结

---

## 二、各节详细说明

### 第一节：概览

概览需要讲清楚两件事。注意：在实际生成的笔记中，这两部分**不使用** a./b. 子标题，用段落自然组织。

**第一件事：论文想要解决的核心问题是什么，包括这个核心问题是如何简化的。**

关键是把论文的研究对象从大领域一步步聚焦到具体问题，讲清楚每一步的边界。读者看完就知道"这篇论文关注的到底是哪一类具体问题"，而不是停留在一个模糊的大方向上。

示例思路：一篇做 MAS 系统的文章 → MAS 系统有很多种 → 这篇文章的研究对象是多个 agent debate 的（每个 agent 生成答案然后互相参考后再生成下一轮，重复迭代后生成最终答案）→ 但这个问题设置跟一般的 workflow 类 agent 系统又不一样 → 讲清楚区别在哪里。

**第二件事：简要讲讲论文提出的方法是什么。**

方法的主干是什么，用了什么算法。不需要展开细节，让读者对方法有一个整体印象即可。

### 第二节：论文怎么定义问题

详细讲解概览中的问题定义部分。包括但不限于：

- 公式化定义（如适用）
- 任务定义
- 约束条件
- 优化目标
- 输入输出是什么

注意：有的论文不适合用公式化定义，可以不写。重点是让读者知道作者到底在优化什么、输入输出是什么。

### 第三节：相关工作

简要梳理相关方向的脉络，重点讲清楚本文方法和已有工作的区别在哪里。不需要面面俱到，聚焦于帮助理解本文定位。

### 第四节：方法与架构

**组织原则：先讲方法的总览，再分开来讲细节，不要一上来就扎进某一个具体子问题。**

理解论文方法的拆分逻辑：

```
论文的背景问题
  → 论文提出的方法发现了什么样的突破口（如何一步一步解决问题）
    → 针对每个突破口做了怎么样的设计解决的
      → 这些设计用到了什么算法
```

递归拆解示例：MAS系统的调优可以先生成拓扑再调优 prompt → 生成拓扑又遇到什么难题（比如发现实验过长，则先训练了一个预测器用来预测脆弱性）→ 调优 prompt 又有什么难题又用了什么方法 → 如此递归拆分。

**本节通常包含：**

- **4.1 方法总览（或架构总览）**：论文通常有架构或算法结构图，需要把图片找出来放在这里，结合图片介绍。如果论文不是某个具体方法而是一个大的架构，则将"方法总览"替换为"架构总览"。
- **4.2 方法细节**：下面拆分出若干 4.2.1、4.2.2 等更细节的子节。每个子节对应一个突破口及其解决方案，按递归拆解的逻辑组织。

### 第五节：评测

按以下顺序组织：

1. **实验设置**：先讲清楚 baseline 怎么选的、benchmark 怎么选的
2. **实验设计**：实验是怎么设置的，为什么要这么设置
3. **实验结果**：讲具体实验结果时需要引用原文的实验结果图/表

### 第六节：总结

- 如果用户有调研目的：结合调研目的讲讲这篇论文的意义
- 如果没有调研目的：讲讲这篇论文的简要总结

## 三、概念提取与 glossary.md 生成（四阶段流程）

概念提取和 glossary 的生成分为四个阶段，严格按顺序执行，不可合并。

### 阶段 1：提取概念，建立大纲（写笔记前）

通读全文后，从以下 5 类概念中提取术语：
1. **Baseline 方法名**：用户可能没读过的对照组论文中的方法
2. **数据集名称**：及其测试什么能力
3. **技术术语和缩写**：论文中出现的专业术语
4. **相关工作中提到的方法**：related work 里引用的方法
5. **论文自定义的新概念/新量**：本文首次提出或定义的概念

此时**只建立 glossary.md 的标题骨架，内容留空**（用 `<!-- TODO -->` 占位）。不要在这个阶段写任何解释——解释在阶段 4 统一生成。

### 阶段 2：撰写精读笔记（大纲完成后）

按六节结构撰写精读笔记。术语首次出现时用 `[[glossary#概念名|概念名]]` 双链标记，引用到 glossary.md 中对应的标题节。`|` 后面是阅读模式下显示的文本。

笔记中需要的概念如果在阶段 1 的 glossary 大纲中没有，**仍然先写上双链引用**，后续阶段会补齐。

### 阶段 3：正则匹配，补齐大纲（笔记写完后）

精读笔记完成后，执行以下操作：
1. 用正则表达式 `\[\[glossary#([^\]|]+)(?:\|[^\]]+)?\]\]` 匹配笔记中所有双链引用，提取概念名
2. 去重后与 glossary.md 中已有的 `## 概念名` 标题逐一对比
3. 将笔记中有而 glossary 中缺失的概念补入 glossary.md，同样只加标题，内容留 `<!-- TODO -->`

这一步确保笔记中引用的每个概念在 glossary 中都有对应条目。

### 阶段 4：逐条生成概念解释（大纲补齐后）

对 glossary.md 中的每一条 `<!-- TODO -->`，逐个生成概念解释。每条解释必须：
- **结合文章语境**：解释要反映这个概念在本文中的含义和角色，不能写成脱离文章的通用词典定义。如果同一术语在其他文献中有不同用法，以本文用法为准
- **使用思维链**：先思考这个概念在本文中出现的上下文（作者为什么提到它？它在论文逻辑链中的位置是什么？），再组织解释语言
- **详略得当**：核心概念、论文自定义的新概念可以写得详细（多段落、必要时举本文中的具体例子）；辅助性概念（如数据集名、简单工具名）可以简洁

解释写入后，将 `<!-- TODO -->` 替换为实际内容。

## 四、图片插入原则

- 原文中有的图尽量在合适的地方插入到笔记中
- 插入时需要结合图片原本的题注理解图片的含义
- 根据有哪些图片再微调精读笔记的结构
- **MinerU 公式图片过滤**：只保留在 Markdown 原文中被明确引用、且有明确图注或明确含义的图片；纯公式截图不保留

## 五、Frontmatter 格式

每篇精读笔记的开头必须包含以下 YAML frontmatter：

```yaml
---
title: 论文标题
year: 发表年份
venue: 具体发表地方（如 AAAI 2025, NeurIPS 2024, arXiv 等）
paper_type: system / method
tags:
  - 论文笔记
  - 精读
---
```

`paper_type` 取值说明：
- `system`：论文主要贡献是一个系统或框架
- `method`：论文主要贡献是一个算法或方法

## 六、glossary.md 示例

以下是一个完整的 glossary.md 示例，展示了从大纲到最终解释的最终状态。注意：解释的详细程度因概念重要性而异——核心概念可以写多段落，辅助性概念保持简洁。

```markdown
---
title: <论文标题> 概念速查
tags:
  - glossary
---

## GRPO

**全称：** Group Relative Policy Optimization

GRPO 是 DeepSeek 提出的一种基于组内相对排序的策略优化算法。与 PPO 不同，GRPO 不需要额外训练一个 critic model（价值网络），而是对每个输入采样一组输出，计算组内相对 reward 来估计 advantage。具体做法是：对于同一个 prompt 生成 G 个 response，用 reward model 打分后减去组内均值并除以标准差，得到归一化 advantage。

在本文中，GRPO 作为 RL 训练的 baseline 之一，作者用它来对比自己提出方法的训练效率和最终效果。选择 GRPO 作为对比对象的原因是它代表了当前 RL for LLM 方向上的主流方案。

## G-Designer

**全称：** G-Designer

G-Designer 是一种用图神经网络（GNN）自动生成多智能体系统（MAS）通信拓扑的方法。输入任务描述，GNN 输出 agent 间的连接关系（即谁和谁通信、以什么结构通信）。它的核心思路是将拓扑搜索建模为图生成问题，而非手工设计。

**本文角色：** 相关工作中的拓扑生成方法。本文作者认为 G-Designer 的局限性在于它只优化拓扑结构而不涉及 prompt 层面的优化，因此本文在此基础上进一步提出了联合优化拓扑和 prompt 的方案。
```

## 七、生成流程总结

子 agent 生成精读笔记时按以下顺序执行：

1. 通读论文全文
2. **阶段 1**：提取概念，生成 glossary.md 大纲（只建标题，内容留 `<!-- TODO -->`）
3. 确认论文中有哪些图片可用
4. **阶段 2**：按六节结构撰写精读笔记，在合适位置插入图片，术语首次出现时添加 `[[glossary#概念名|概念名]]` 双链标记
5. **阶段 3**：正则匹配笔记中所有双链引用，对比 glossary 标题，补齐缺失条目
6. **阶段 4**：逐条生成 glossary 概念解释——结合文章语境，使用思维链，详略得当
7. 添加 frontmatter
8. 公式格式检查
9. 最终自查（确认所有引用都有对应条目，无 TODO 残留）
